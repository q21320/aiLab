# 设备接入：方式说明 · 维护指南 · 功能审查

> 本文基于当前代码实际行为编写，所有"缺陷"均经实际运行验证，非推测。
> 验证环境：Docker 部署版（http://localhost:3800）

---

# 一、设备接入方式

## 1.1 支持的协议

平台共 **4 种驱动**（`backend/iot/drivers.mjs`），统一实现 `probe / read / write` 三接口：

| 协议 ID | 名称 | 适用设备 | 地址配置 |
| --- | --- | --- | --- |
| `scpi` | SCPI 仪器（TCP） | 可编程电源、万用表、示波器、材料试验机 | `host` + `port`（默认 5025） |
| `modbus-tcp` | Modbus TCP | 环境试验箱、PLC、电表/能耗表 | `host` + `port`（默认 502）+ `unitId` |
| `http` | HTTP / REST | 带 REST 接口的新仪器、边缘网关 | `baseUrl` + `token`（可选） |
| `mock` | 平台模拟设备 | 无硬件演示（数据由内置模拟器生成） | 无需配置 |

> ⚠️ 文件头注释提到 `mqtt（订阅）`，但**代码中并不存在 MQTT 驱动**，`DRIVERS` 注册表只有上述 4 个。注释与实际不符。

## 1.2 接入步骤（UI 操作）

进入 **工业物联 → 设备接入** 页面：

1. **点「接入真实设备」**
2. 选择协议 → 系统自动填充示例点位（`applyTemplate`）
3. 填写连接地址
4. **按仪器手册修改点位表**（关键步骤，见 1.3）
5. 保存

## 1.3 点位表配置（最容易出错的地方）

点位表决定了每一条数据怎么从设备里取出来。

### SCPI 点位字段

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| `key` | 内部标识（程序用） | `temperature` |
| `label` | 显示名称 | `实测温度` |
| `query` | 读取命令 | `MEAS:TEMP?` |
| `command` | 下发命令模板，`{value}` 为占位符 | `SOUR:TEMP {value}` |
| `unit` | 单位 | `℃` |
| `scale` / `offset` / `decimals` | 数值换算与保留位数 | `0.1` / `0` / `2` |

### Modbus 点位字段

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| `register` | 寄存器地址 | `0` |
| `type` | 数据类型 | `int16` / `uint16` / `int32` / `uint32` / `float32` |
| `fc` | 功能码 | `3`（保持寄存器，默认）或 `4`（输入寄存器） |
| `order` | 32 位字节序 | `AB`（默认）或 `CD` |
| `scale` / `offset` | 换算：`实际值 = 原始值 × scale + offset` | `0.1` |

> **实测提醒**：我第一次接入虚拟仪器时写了 `MEAS:HUM?`，仪器返回 `ERROR:UNKNOWN_COMMAND`，
> 正确命令是 `MEAS:HUMI?`。**点位表填错，读取结果里的 `raw` 字段会带原始错误信息**，看 raw 就能定位。

## 1.4 接入后的三类操作

### 探测（probe）
对设备执行 `*IDN?`（SCPI）或读首个寄存器（Modbus），返回厂商/型号/序列号/固件。用于**验证通信是否通**。

### 读取（read）
按点位表逐点读取，结果写入设备状态、历史曲线、SSE 实时流（大屏可订阅）。

### 下发（write）
写设备。已实现两项关键防护：
- SCPI 仪器返回 `ERROR:...` 时判定为**失败**（不再误报成功）
- 下发后**自动回读**，界面展示「下发前值 → 目标值 → 回读实测值」

# 二、后续维护指南

## 2.1 日常维护清单

| 周期 | 事项 | 操作 |
| --- | --- | --- |
| 每日 | 查看设备状态 | 设备接入页顶部统计条 |
| 每日 | 处理告警 | 仪表盘「实时告警」面板（⚠️ 目前**无法在界面确认**，见 3.2） |
| 每周 | 检查采集数据完整性 | 设备「曲线」弹窗看是否有断点 |
| 每月 | 备份数据库 | `pg_dump`（见 2.4） |
| 按需 | 修改点位表 | 设备行 → 编辑（⚠️ 需要能力，见 3.3） |

## 2.2 虚拟仪器（无硬件联调）

设备接入页顶部 → **「启动虚拟仪器」**，会启动：
- SCPI 服务：`127.0.0.1:5025`
- Modbus TCP：`127.0.0.1:5020`
- 型号：VC-300

| 支持的 SCPI 命令 | 说明 |
| --- | --- |
| `*IDN?` | 设备识别 |
| `MEAS:TEMP?` / `MEAS:HUMI?` / `MEAS:POW?` | 读温度/湿度/功率 |
| `SOUR:TEMP <值>` | 设定温度 |
| `SYST:STAT?` / `SYST:CYCL?` | 状态/循环次数 |

> **重启后端后虚拟仪器会停止**，必须重新点「启动虚拟仪器」。我测试时踩过 `ECONNREFUSED`。

## 2.3 接真实仪器的注意事项

| 项目 | 说明 |
| --- | --- |
| 网络 | 后端所在机器必须能访问仪器 IP；跨网段需确认路由 |
| 防火墙 | 放行仪器端口（5025 / 502 / 自定义） |
| SCPI | 仪器需开启 TCP socket 模式（多数仪器默认 SCPI-RAW） |
| Modbus | 需知道寄存器地址、数据类型、字节序；**厂商手册的地址可能是 0基或1基，需试** |
| HTTP | 需要仪器有 REST API，或经过网关转换 |
| 串口设备 | 目前**不支持原生串口**，需用串口服务器转 Modbus TCP |

## 2.4 数据库备份与恢复

```bash
# 备份
docker exec ailab-postgres-1 pg_dump -U ailab -d ailab > backup-$(date +%Y%m%d).sql

# 恢复
docker exec -i ailab-postgres-1 psql -U ailab -d ailab < backup-20260101.sql
```

## 2.5 故障排查

| 现象 | 排查方向 |
| --- | --- |
| 探测失败 `连接失败` | IP/端口错误，或仪器未开机/网络不通 |
| 读取返回 `ERROR:UNKNOWN_COMMAND` | 点位 `query` 命令拼写错误，查仪器手册 |
| 读取值明显不对 | Modbus 的 `scale`/`order`/`type` 配置错误 |
| 读数为 `null` | 该点位 `query` 为空（SCPI 会被跳过） |
| 下发「成功」但设备没反应 | 已回读验证；若回读值未变，检查仪器是否接受该命令 |
| 设备显示 online 但实际断网 | **已知缺陷，见 3.1** |

# 三、功能完善度审查

## 3.1 🔴 重大缺陷：真实设备没有自动采集

**这是设备接入功能最核心的缺失。**

| 项目 | 现状 |
| --- | --- |
| 模拟设备（mock） | 每 2 秒自动采集（`setInterval(simulateTick, 2000)`） |
| 真实设备（SCPI/Modbus/HTTP） | **只有手动点「读取」或跑自动化测试才采集** |

**实测验证**：接入一台 SCPI 设备后等待 9 秒（不点读取），采集点为 **0 个**；手动点一次读取后才有 1 个点。

**影响**：
- 设备接入后，大屏/历史曲线**不会自动更新**，必须人工点「读取」
- 真实设备超限**不会自动告警**（告警只在采集时判定）
- 「工业物联网实时数据驱动低代码平台」这一需求（4.6）在两台设备之间**体验割裂**：演示用的模拟设备是实时的，真设备是手动的

**建议**：增加可配置的轮询调度器（每台设备独立采集周期，默认 10s），后台常驻运行。

## 3.2 🟠 告警只能产生、无法处理

| 项目 | 现状 |
| --- | --- |
| 告警产生 | ✅ 正常（实测已累积 364 条） |
| 告警展示 | ✅ 仪表盘「实时告警」显示最近 5 条 |
| 告警确认（ack） | ❌ **后端接口存在，但前端无处调用** |
| 告警处理闭环 | ❌ 无 |
| 告警列表页 | ❌ 不存在（只能看到最近 5 条） |

**实测**：`grep ackAlert frontend/src/views/iot/index.vue` → **0 处调用**。364 条告警一直累积，用户无法标记"已处理"。

**建议**：新增告警管理页（筛选/分页/确认/批量确认），这是运维的刚需。

## 3.3 🟠 设备状态不反映真实连通性

**实测**：停掉虚拟仪器后，对设备执行读取返回 `connect ECONNREFUSED`，但设备状态**仍然显示 `online`**。

设备 `status` 字段只在接入时设置，之后**从不根据通信结果更新**。

**影响**：运维无法通过界面判断设备是否真的在线。

**建议**：读取/探测失败时置为 `offline` 并记录 `lastError`；成功时恢复 `online`。

## 3.4 🟠 接入时完全没有校验

**实测**：提交一个只有 `key` 没有 `query` 的点位，**接入成功**（DEV-009），要到读取时才失败。

未校验项：
- 必填字段（SCPI 的 `query`、Modbus 的 `register`）
- IP/端口格式合法性
- 点位 `key` 是否重复
- `type` 是否在支持范围内

**建议**：接入时按协议 schema 校验，保存前给出明确错误。

## 3.5 🟠 连接不复用，点位串行读取

`scpiCommand` / `modbusTCP` **每次调用都新建 TCP 连接**，且点位是 `for` 循环串行读。

- 本地虚拟仪器响应快（约 5ms），看不出问题
- 真实仪器单次命令常需 50–200ms，**10 个点位 × 150ms ≈ 1.5 秒**
- 再加上轮询，设备多时会堆积

**建议**：驱动层维护连接池；同设备多寄存器合并为一次批量读（Modbus 支持一次读多个连续寄存器）。

## 3.6 🟡 设备操作没有审计日志

**实测**：审计日志里只有「登录」记录（7 条），**没有设备接入/读取/下发的记录**。

而需求 4.9 明确要求"排产/样品全埋点"，设备下发属于影响物理设备的操作，**更应该有审计**。

**建议**：设备接入/删除/下发/修改点位 均写入审计日志。

## 3.7 🟡 协议覆盖不全

| 协议 | 状态 |
| --- | --- |
| SCPI | ✅ |
| Modbus TCP | ✅ |
| HTTP | ✅ |
| MQTT | ❌ **注释提到但未实现** |
| OPC UA | ❌ 工业场景常用，未支持 |
| Modbus RTU / 串口 | ❌ 需串口服务器转换 |
| CAN / PROFINET | ❌ |

**建议**：至少补齐 MQTT（工业网关最常见），并修正文件头注释。

## 3.8 🟡 HTTP 驱动错误信息不友好

**实测**：读取不可达地址返回 `{"ok":false,"error":"fetch failed"}`，没有 URL、没有状态码。

且 `write` 不检查 `res.ok`，**HTTP 500 也会返回成功**（读代码确认，未实测）。

**建议**：错误信息带 URL 与状态码；write 检查响应状态。

## 3.9 🟡 其他

- **Modbus float32 写入忽略 `order`**：读路径支持 AB/CD，写路径永远按 AB 下发（`drivers.mjs:227`）
- **无设备分组/标签**：设备多了只能靠位置字段
- **无采集数据保留策略**：`histories` 是内存环形缓冲（200 点/设备），**重启即丢失**，未入库
- **自动化测试与设备接入页数据不互通**：测试采集的数据不会自动成为设备的"当前值"

# 四、总结

## 已经做得不错的部分

- ✅ 4 种驱动统一接口，扩展新协议只需实现 3 个方法
- ✅ 虚拟仪器让无硬件环境也能完整验证链路
- ✅ 下发有错误检测 + 自动回读验证（这是我上一轮补的）
- ✅ SCPI/Modbus 底层协议实现正确（实测能读能写）
- ✅ 点位支持换算（scale/offset/decimals）与 32 位类型/字节序

## 距离"完善"还差什么

| 优先级 | 事项 | 工作量估计 |
| --- | --- | --- |
| 🔴 P0 | 真实设备自动轮询采集 | 1–2 天 |
| 🟠 P1 | 告警确认闭环 + 告警管理页 | 1 天 |
| 🟠 P1 | 设备状态跟随通信结果 | 0.5 天 |
| 🟠 P1 | 接入时校验配置 | 0.5 天 |
| 🟡 P2 | 连接复用 + 批量读寄存器 | 1 天 |
| 🟡 P2 | 设备操作审计日志 | 0.5 天 |
| 🟡 P2 | MQTT 驱动 | 1–2 天 |
| 🟡 P3 | 采集数据入库 + 保留策略 | 1 天 |

**一句话结论**：设备接入的**"接入"能力（驱动 + 探测 + 读写）基本可用**，
但**"持续运行"能力（自动采集、状态监测、告警闭环）尚未完成**——
目前更像"设备调试工具"，还不是"生产级 IoT 接入平台"。演示时建议用模拟设备，
真实设备演示前需要接受"手动点读取"这一限制。
