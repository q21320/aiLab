## 二、上线后可能出现的新问题

以下是**引入上述功能后新产生的风险**，按严重度排序。

### 🔴 N1. 轮询会消耗真实设备的连接/寿命

采集调度器现在会**持续**访问设备。对虚拟仪器无所谓，但真实场景要注意：

- **SCPI 仪器**：部分老式仪器同时只允许 1-2 个 TCP 连接。如果运维人员在仪器面板上手动操作，而我们同时在轮询，可能被仪器拒绝
- **PLC / 试验箱**：小型 PLC 的连接槽位有限（常见 8-16 个）。设备多时可能耗尽
- **电池供电设备**：持续轮询会明显缩短续航

**缓解**：默认 10 秒周期已比较保守；建议在接入文档里要求按设备能力配置，工业 PLC 建议 ≥5 秒。

### 🔴 N2. 连接池会掩盖"设备已更换"的问题

SCPI 连接池保持长连接 30 秒。如果这期间设备**重启或换 IP**，池里的连接可能已失效，但代码会先复用它、等超时才发现。

**影响**：故障发现延迟最多 1 个采集周期 + 4 秒超时。

**缓解**：出错时已销毁连接并重新建连，最多损失一轮采集。可接受。

### 🟠 N3. 采集失败退避可能导致"长时间看不到数据"

我实现了**指数退避**：失败 1 次等 10s，2 次等 20s，3 次等 40s……上限 5 分钟。

**副作用**：设备恢复后，最坏情况要等 **5 分钟**才重新采集到。

**影响**：运维会觉得"设备明明好了，界面还是离线"。

**缓解方案**（建议后续加）：提供一个「立即重连」按钮，或把退避上限降到 1 分钟。

### 🟠 N4. 告警量大时，ack 是逐条调用

告警管理页的「批量确认」是**串行逐条 PUT**。当前库里有 400+ 条未处理告警，全选确认会发 400 多个请求。

**影响**：批量确认会很慢（每条约 20ms，400 条 ≈ 8 秒），期间界面卡在 loading。

**缓解**：后端应提供 `POST /api/iot/alerts/ack-batch`（一次更新多条）。当前实现只是权宜。

### 🟠 N5. 告警表上限 100 条，会持续淘汰

`iotState.alerts` 上限 100 条，超出时优先保留 open 状态、淘汰已确认的。

**问题**：
- 当前已有 **425 条未处理告警**（模拟设备每 2 秒可能产生），而数组只保留 100 条
- 也就是说：**告警记录正在被静默丢弃**，数据库里的 `iot.json` 只是内存快照
- 告警没有独立入库，**重启后只保留最后一次写入的 100 条**

**这是本轮修复后仍然存在的隐患**：告警虽然能确认了，但**没有持久化的告警历史表**。

**建议**：告警应像审计日志一样写入独立表（PostgreSQL `iot_alerts`），支持分页查询与长期留存。

### 🟠 N6. 校验可能挡住在用的设备

新增的校验是**阻断式**的：校验不通过直接 400。

**风险**：如果存量设备的数据本身就有问题（例如点位 key 含大写字母、老数据缺 `address`），用户下次「编辑保存」时会被挡住，**产生"以前能改、现在改不了"的抱怨**。

**缓解**：应为已有设备提供「宽松模式」（只警告不阻断），或提供数据修复脚本。

### 🟡 N7. 自动采集让"数据量"指数增长

之前只有手动读取，现在每台设备每 10 秒采集一次。10 台设备 = 每分钟 60 次采集 = 每天 86,400 条点位。

**问题**：
- `histories` 是**内存环形缓冲**（每设备 200 点），重启即丢失
- 但这 200 点现在**被快速填满**，历史曲线只能看到最近 33 分钟
- 大屏的「历史趋势」会变成"最近半小时趋势"

**建议**：采集数据应写入时序表（或按小时归档），否则"历史"名不副实。

### 🟡 N8. 真实设备 + 模拟设备同时跑，数据会混

模拟设备仍然每 2 秒自动生成数据（`simulateTick`），真实设备独立轮询。

**问题**：
- `iotState.devices` 里两种设备混在一起，概览统计（在线数、今日能耗）把两者相加
- 演示时如果客户看到"模拟设备"和"真实设备"数据混在一个大屏里，会质疑真实性

**建议**：概览统计区分「真实/模拟」，或提供「演示模式」开关一键隐藏模拟设备。

### 🟡 N9. 前端定时器与 SSE 的竞争

设备采集通过 SSE 推送（`broadcast`），前端 `iotLive` 收到后更新；同时前端还有定时拉取。

**问题**：如果某次 SSE 推送丢失（网络抖动），前端数据会停在旧值，直到下次手动刷新。

**缓解**：SSE 断线重连已有，但**断线期间的数据缺口不会补齐**。

### 🟢 N10. 容器内时区

本轮给 release compose 加了 `TZ=Asia/Shanghai`，但**主 compose 没有加**。

**影响**：采集时间显示可能是 UTC（比北京时间晚 8 小时），审计日志时间戳也会偏。

**建议**：主 compose 也加上 `TZ`。

## 三、更远期的架构性风险

| 风险 | 说明 | 何时会爆发 |
| --- | --- | --- |
| **轮询模型不可扩展** | 每台设备一个定时检查，100 台设备 = 每秒 100 次判断。当前实现没问题，但到 500+ 设备会明显 | 设备数 > 200 |
| **无消息队列** | 点位数据直接进内存 + SSE，没有缓冲。数据库写入是"整份覆盖"（`kv_documents.iot`），采集量大时 IO 压力大 | 采集频率 < 5s 且设备 > 20 |
| **单实例架构** | 采集调度器跑在应用进程里。如果部署 2 个实例，**两台都会轮询同一设备**，数据重复 | 需要高可用时 |
| **无设备分组/租户** | 所有设备平铺，没有分组、标签、租户隔离 | 客户要求多实验室隔离时 |
| **无证书/加密** | SCPI 明文 TCP，HTTP 驱动用 http:// | 对接安全要求高的客户时 |

## 五、一个必须提醒的现实问题

本轮让**真实设备能自动采集**了，但这意味着：

> **接上真实设备后，系统会每 10 秒对设备发一次命令。**

在实验室环境这没问题，但如果对接的是**生产设备**（尤其是 PLC 控制的产线），
持续轮询前需要和设备厂商确认：
- 该设备是否允许高频外部读取
- 读取是否会影响设备主控逻辑
- 是否需要专用的只读数据通道

**这不是代码问题，是工程规范问题**，建议写进接入前置条件。

## 六、告警入库（本轮已实现）

### 6.1 问题回顾

原实现中告警只存于 `iotState.alerts` 内存数组，上限 100 条。
升级前的实测数据：**内存里只有 100 条，而实际已产生 546 条**——
意味着其中 **446 条告警被静默丢弃**，从未有人看到。

### 6.2 实现内容

新增 `backend/iot/alerts.mjs` + `iot_alerts` 表：

| 能力 | 说明 |
| --- | --- |
| 全量持久化 | 每条告警写入 PostgreSQL，**不再因条数上限丢弃** |
| 迁移 | 首次启动自动把旧 JSON 中的存量告警导入（实测迁移 546 条） |
| 分页查询 | `GET /api/iot/alerts?page=&pageSize=&status=&level=&keyword=` |
| 统计 | `GET /api/iot/alerts/stats`（总数/未处理/严重/预警/已确认） |
| 单条确认 | `PUT /api/iot/alerts/:id/ack`（记录确认人与时间） |
| 批量确认 | `PUT /api/iot/alerts/ack-batch`（传 ids 数组，或 `?all=1`） |
| 留存清理 | 每天自动删除 12 个月前的**已确认**告警，未处理的不删 |
| 索引 | `time` / `(status,time)` / `(device_id,time)` 三个索引 |

内存数组仍保留，但只作为**最近 200 条的实时缓存**（供 SSE 推送与首页概览），
统计数字一律以数据库为准。

### 6.3 验证结果

| 验证项 | 结果 |
| --- | --- |
| 存量告警迁移 | ✅ 546 条自动导入 |
| 分页查询 | ✅ total=546，翻页正常 |
| 统计准确性 | ✅ 未处理/严重/预警分别正确 |
| 批量确认 546 条 | ✅ 一次请求完成，未处理归零 |
| 新告警持续写入 | ✅ 确认后 8 秒内产生 4 条新告警 |
| 重启后保留 | ✅ 552 条 → 重启后 562 条（含新增），完整保留 |
| 确认人记录 | ✅ `ackedBy=管理员` 正确写入 |

### 6.4 前端变化

**告警管理页**（`/alerts`）：
- 统计卡改为数据库真实数字（原来只统计内存中的 100 条）
- 分页（20/50/100 每页），不再只显示最近若干条
- 「确认本页」与「全部确认」两个批量按钮（原来逐条串行请求，546 条要 10 秒+）
- 设备列同时显示名称与 ID
- 已确认记录显示确认人

**仪表盘**：「未处理告警」数值改由数据库统计，每 5 秒刷新。

### 6.5 仍未解决的关联问题

| 问题 | 状态 |
| --- | --- |
| 采集数据（点位曲线）未入库 | ⚠️ 仍是内存环形缓冲，历史只有约 33 分钟 |
| 告警与采集数据的关联 | ⚠️ 告警记录了时间点，但无法跳转到当时的曲线 |
| 告警通知（邮件/短信/IM） | ❌ 未实现，目前只能登录系统查看 |
| 告警升级策略（超时未确认自动升级） | ❌ 未实现 |

**下一步建议**：采集数据入库（同样用独立表 + 按小时归档），
这是让「历史曲线」名副其实的前提。

## 七、采集数据入库（本轮已实现）

### 7.1 问题回顾

此前点位数据只存在 `histories` 内存环形缓冲（每设备 120 点）。
开启自动采集后（每 10 秒一次），**120 点 ≈ 20 分钟就被填满**，
历史曲线实际只能看最近 20~33 分钟，且**重启即全部丢失**。

### 7.2 实现内容

新增 `backend/iot/points.mjs` + `iot_points` 表：

| 能力 | 说明 |
| --- | --- |
| 全量持久化 | 每次采集写入数据库，支持任意时间跨度查询 |
| 批量写入 | 内存缓冲 2 秒 / 200 条批量 INSERT，避免高频单条写库 |
| 历史查询 | `GET /api/iot/devices/:id/live?from=&to=&limit=&bucketMs=` |
| 时间桶降采样 | `bucketMs` 参数按时间桶取平均值，长时间跨度不会返回海量点 |
| 统计 | `GET /api/iot/points/stats`（总量/设备数/最旧/最新/占用空间） |
| 留存清理 | 默认 90 天（`IOT_POINT_RETENTION_DAYS` 可调），每天自动清理 |
| 索引 | `(device_id, time DESC)` 与 `(time DESC)` |

**双写架构**：内存缓冲（120 点）保留给 SSE 实时推送与秒级曲线，
数据库保存完整历史。查询时按是否带时间范围自动路由：
- 不带范围 → 内存（实时，低延迟）
- 带范围 → 数据库（历史，完整）

### 7.3 修复的写入遗漏

发现 `backend/iot/api.mjs` 有**两处直接操作 `histories`**（自动测试采集、手动读取），
绕过了统一入口，导致真实设备的点位**不会进数据库**。

已改为统一注入 `recordPoint` 入口，所有采集路径（模拟器 / 真实设备轮询 / 手动读取 / 自动化测试）
都走 `pushHistory` → 内存 + 批量落库。

### 7.4 验证结果

| 验证项 | 结果 |
| --- | --- |
| 点位落库 | ✅ 100 条 / 5 台设备 |
| 历史查询（数据库） | ✅ source=db，温度范围 32.3~38.2℃ |
| 时间桶降采样 | ✅ 24 点聚合为 5 桶 |
| 实时模式 | ✅ source=memory，走内存缓冲 |
| 重启后保留 | ✅ 130 → 180 条，重启前数据仍可查 |
| 统计接口 | ✅ 显示占用空间 120kB |

### 7.5 前端变化

**设备曲线弹窗**新增时间范围选择：

| 选项 | 数据来源 |
| --- | --- |
| 实时 | 内存缓冲，2 秒自动刷新 |
| 10 分钟 / 1 小时 / 24 小时 / 7 天 | 数据库查询，自动降采样（查看历史时停止自动刷新） |

### 7.6 数据量规划

按 10 台设备 × 10 秒周期估算：

| 周期 | 行数 |
| --- | --- |
| 每天 | 86,400 行 |
| 90 天（默认留存） | 约 780 万行 |
| 磁盘占用 | 约 1-2 GB（含索引） |

若设备更多（>50 台）或周期更短（<5 秒），建议：
1. 缩短留存期至 30 天
2. 或引入时序数据库（TimescaleDB 的 hypertable、或 InfluxDB）
3. 或增加「降采样归档表」：原始数据保留 7 天，之后只保留小时级聚合值

### 7.7 仍未解决

| 问题 | 说明 |
| --- | --- |
| 告警与曲线无法跳转 | 告警记录了时间点，但界面上点击告警不能跳到当时曲线 |
| 无数据保留策略界面 | 留存天数只能改环境变量，没有 UI |
| 无导出功能 | 历史数据不能导出 CSV/Excel |
| 实时曲线有轻微断点感 | 批量写入间隔 2 秒，与 SSE 推送节奏不完全一致（不影响数据库） |

## 八、告警联动与运维能力（本轮已实现）

补齐第七节遗留的三项：告警跳转曲线、留存可视化配置、历史数据导出。

### 8.1 告警 → 曲线定位

**实现**：告警管理页每条告警新增「曲线」按钮，跳转到
`/iot?device=<deviceId>&time=<告警时间戳>`，设备接入页自动：
1. 等待设备列表加载
2. 打开该设备曲线弹窗
3. 切换到「1 小时」历史窗口，**以告警时刻为中心**（前 60 分钟 ~ 后 5 分钟）
4. 顶部显示「已定位到告警时刻」提示

**设计考量**：告警发生后关注的是**前因后果**，所以窗口以告警时刻为中心而非从告警时刻开始。

**验证**：以告警时刻 ±60 分钟查询，返回 236 个历史点，`source=db`。

### 8.2 留存天数可视化配置

| 项目 | 说明 |
| --- | --- |
| 入口 | 设备接入页 → 「数据留存设置」 |
| 接口 | `GET/PUT /api/iot/settings` |
| 权限 | 修改需**工程师及以上**（访客/未登录被拒，已验证 401/403） |
| 范围 | 1 ~ 3650 天，非法值返回 400 |
| 展示 | 实时显示点位总量、设备数、占用空间、最早数据时间 |
| 审计 | 修改操作写入审计日志 |

**说明**：留存天数只影响**采集点位**；告警留存固定 12 个月，审计日志 36 个月。

### 8.3 历史数据导出 CSV

| 项目 | 说明 |
| --- | --- |
| 入口 | 曲线弹窗底部「导出当前范围 CSV」 |
| 接口 | `GET /api/iot/points/export.csv?deviceId=&from=&to=` |
| 内容 | 设备ID、时间、温度、湿度、功率 + **动态扩展列**（自定义点位 key） |
| 上限 | 单次 10 万行（防内存爆） |
| 安全 | 复用统一 CSV 转义（防公式注入），带 BOM 便于 Excel 打开 |
