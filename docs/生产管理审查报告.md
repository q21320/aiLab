# 生产管理模块 · 功能审查报告

> 审查范围：`frontend/src/views/production/`（index.vue 439 行、GanttBoard.vue 219 行）
> 与 `frontend/src/stores/production.ts`（360 行）。
> 结论：**功能覆盖较全（订单/排产/工单/异常/产能五个模块齐备），
> 但排产算法是本模块的核心，目前实现过于简化，且数据未接入后端。**

## 二、核心问题：排产算法不完整

### 2.1 🔴 订单数量（qty）完全不参与排产

```js
// production.ts:246 scheduleOrder()
for (const p of this.processes) {
  ...
  cursor += p.hours * 3600000;   // ← 只用固定工序时长
}
```

**后果**：订单 A（1200 件）与订单 B（3000 件）的排产耗时完全相同。
现实中 3000 件应该是 1200 件的 2.5 倍工时。

### 2.2 🔴 产线日产能（hoursPerDay）定义了却从不使用

产线数据里明确有：

```js
{ id: "LN-1", name: "SMT 生产线", type: "SMT", hoursPerDay: 16 }
{ id: "LN-3", name: "装配线", type: "ASSEMBLY", hoursPerDay: 8 }
```

但排产时把它们当作 **7×24 不间断可用**，完全没有：
- 每天只工作 N 小时的限制
- 班次切换（早/中/夜班）
- 周末/节假日
- 换线准备时间（changeover time）

**后果**：排出来的计划在现实中根本执行不了。比如装配线每天只开 8 小时，
系统却可能排出连续 16 小时的装配工单。

### 2.3 🔴 交期（due）不参与排产，也不做逾期预警

交期字段存在、能显示，但：
- 排产时不考虑交期
- 排完后不检查"是否超期"
- 界面上没有任何逾期高亮或提醒

**后果**：可能排出一个必然逾期的计划，而系统无任何提示。

### 2.4 🟠 优先级（priority）不生效

订单有 `high / normal / low` 三档优先级，但：
- 「自动排产」按数组顺序排（先创建的先排）
- 加急订单不会提前

```js
// index.vue:196
store.orders.filter((o) => o.status === 'draft').forEach((o) => store.scheduleOrder(o.id));
// ↑ 按数组自然顺序，与 priority 无关
```

### 2.5 🟠 排产只支持"串行工序"，无并行

当前算法：工序 A 完成后才开始工序 B，依赖链严格串行。

现实中常见：
- 多个子件并行加工，最后总装
- 同工序可拆到多条产线并行

### 2.6 🟠 排产窗口硬编码 7 天

```js
const windowStart = dayStart(0);      // 今日 9:00
const windowEnd = dayStart(7);        // 7 天后
```

排不下就直接 `return false`，用户可能不知道失败原因（没有返回具体原因）。

## 三、数据与持久化问题

### 3.1 🔴 排产数据只存在浏览器 localStorage

```js
const LS_KEY = "ailab.production.v1";
```

**后果**：
- 换浏览器/换电脑数据全丢
- 清缓存数据全丢
- 多人无法协同（每个人看到自己的数据）
- 无法与样品、IoT、审计等已入库的模块联动

**这是与其他模块最大的不一致**：样品、设备、告警、审计都已进 PostgreSQL，
唯独排产还在浏览器本地。

### 3.2 🟠 ID 生成仍依赖前端计数器

虽然已修复"刷新后重号"，但根本方案应是后端生成。
多端并发创建订单时仍可能重号。

## 六、改进建议（按投入产出排序）

### 第一批：让排产算法真正可用（1-2 天）

1. **引入工序产能模型**
   ```js
   // 加工时间 = 数量 / 每小时产能
   const durationH = qty / (process.ratePerHour || 1);
   ```
   或者在工序上增加 `标准工时/件` 字段。

2. **按产线工作时间排产**
   - 产线增加班次配置（如 8:00-20:00）
   - 排产时跳过非工作时段
   - 跨天自动接续

3. **加入交期检查**
   - 排产完成后对比 `due`
   - 逾期订单在界面上标红并提示"预计逾期 N 天"

4. **优先级排序**
   - 「自动排产」按 `priority` 降序 + 交期升序处理

### 第二批：数据入库（1-2 天）

5. 排产数据迁入 PostgreSQL（与样品/设备一致）
   - 表：`production_orders` / `work_orders` / `processes` / `lines` / `production_exceptions`
   - 接口：与表单/CRUD 相同的风格

### 第三批：体验补齐（2-3 天）

6. 工单进度可录入（弹窗输入实际进度与耗时）
7. 排产结果预览确认
8. 导出 CSV
9. 甘特图缩放与滚动

### 第四批：高级能力（按需）

10. 产能负荷分析图（各产线每日占用率）
11. 计划 vs 实际对比报表
12. 多方案模拟对比

## 七、总结

**做得好的地方**：
- ✅ 五个子模块齐全，覆盖订单→排产→执行→异常→产能的完整流程
- ✅ 甘特图交互完善（拖拽、冲突检测、实时时间线）
- ✅ 冲突检测确实实现了（红色虚线标识同产线重叠）
- ✅ 工序与产线的数据模型设计合理

**最需要改进的**：
- 🔴 **排产算法是"演示级"的**：不考虑数量、产能、交期、优先级，排出的计划不可执行
- 🔴 **数据只在浏览器**：换设备就丢，无法协同，与其他模块割裂

**一句话结论**：
生产管理的**框架和交互做得不错**，但**排产这个核心能力目前只是"能排出东西"，
还不是"能排出可执行计划"**。如果这个模块要交付给真实工厂使用，
第一批建议（产能、班次、交期）是必须做的。
